# Agent Note: 原版激光目标跟踪效果验证

Status: implemented

## Problem

小车需要跟踪指定的人，但现有两次移植同时改变了输入选择、目标关联或丢失判定，无法用现场效果判断参考实现本身是否适用。先让小车静止，保留参考实现的目标跟踪与滤波行为，观察人在正常步速下的目标位置，再决定是否改进算法。车辆跟随后续通过现有 Nav2 导航栈设计。

## Decision

分支从 `b9653890` 建立。以 [6-robot/jie_deamon 固定提交 `9403185c0cf99a0b415ddd4f3b4215b44dd0809c`](https://github.com/6-robot/jie_deamon/tree/9403185c0cf99a0b415ddd4f3b4215b44dd0809c) 为唯一参考版本，原样复制完整的 `LidarTracker`、`KalmanFilter2D` 及其直接依赖的参考头文件；复制件与固定提交逐文件比对，参考源码改动为零。复制代码保留来源与许可信息。原版内部虽计算势场和跟随速度，跟踪节点不注册速度回调，也不创建跟踪速度发布者。

原版 `processScan` 消费 `LaserScan`，本仓库输入是 10 Hz 设计的 `/points_raw`。独立 ROS 跟踪包只在参考源码之外实现点云桥接、ROS 输入输出和目标选择。桥接先按原始点云的 `ring` 字段选最接近 0° 的水平环：Vanjee 722 使用 `ring=26`，仿真 16 线雷达使用 `ring=7`。随后按点云时间戳将该环的有效回波变换到 `base_footprint`，不按变换后的高度选择点，也不合并其他环。

桥接以平台 Profile 的每圈列数建立内部 `LaserScan`：实车 1200 格、仿真 1800 格。按水平角填格，空格填无穷大，同格保留最近回波。角度在桥接层适配原版 `point_x=-range*cos(angle)`、`point_y=-range*sin(angle)` 的方向约定，使原版处理后的坐标为 `base_footprint` 的前 X、左 Y；这个内部扫描不作为标准 `/scan` 对外发布。不给桥接增加聚类、目标预测、距离或高度带筛选。TF 不可用或输入字段不满足契约时跳过该帧并报告接口错误，不制造目标观测。

目标由 Web 局部视图双击任意位置直接设置搜索中心，沿用原版的搜索圆内全部有效回波求质心、未匹配时保留目标位置的行为。卡尔曼源码原样保留，开关默认关闭，与原版一致；不添加丢失超时、预测中或已丢失状态，也不把 3.33 Hz 的旧判断写入配置。Web 显示手动控制、自动导航、目标跟踪三种页面模式；手动页通过仅含自动导航和目标跟踪按钮的抽屉选择模式。跟踪页展示单环回波、搜索圆和最后一次目标位置，可拖动、缩放、适配及居中，双击选点按当前视图反算坐标；不显示手动行驶、导航或停车控件。浏览器刷新只读取节点当前目标。跟踪页面保持 gate 为 `manual`，不发送导航目标；自动导航返回手动控制仍调用 gate 接管服务，已有 Nav2 goal 不因此取消。

系统使用现有 `system_bringup` 正式入口启动，没有专用验证系统，也不改 `bringup.yaml` 默认模式。静止验证可使用现有 `mapping` 或 `navigation` 模式，在不发导航目标的情况下保持车辆静止。当前系统事实由 `docs/architecture.md`、`docs/development.md`、`docs/testing.md` 记录。

### 设计取舍

`bc18d410` 中的跟踪提案只作为审阅输入；下表记录各项取舍，不表示旧提案被整体接受。

| 审核项 | 本次取舍 |
|---|---|
| 静止小车先验证定位，车辆后续走 Nav2 | 保留 |
| 三维点云先变到小车坐标系，再取有限高度带 | 改为先取最接近 0° 的原始单环，再作坐标变换 |
| 以 1～3 米为默认有效距离 | 撤回新增距离限制，先看参考实现原有行为 |
| 聚类、预测位置关联与候选点簇确认 | 撤回，保留原版搜索圆和双击任意位置设目标 |
| 默认启用并按观测时间戳改写卡尔曼 | 撤回，原版源码和默认关闭状态均不改 |
| 预测中、超时丢失和失联锁存 | 撤回，原版无匹配时保留位置，不新增超时 |
| Web 局部俯视展示 | 保留，但使用单环回波与原版目标输出 |
| 抽屉选择导航或跟踪，跟踪不接管速度 | 保留，现有 gate 和导航任务行为不变 |
| 无地图专用跟踪启动链 | 撤回，使用现有完整 `mapping` 或 `navigation` 启动 |
| 现场移动目标验收后再设计车辆跟随 | 保留；首次验收只评估原版效果 |

### 实现与现场边界

代码包含原样复制的三个参考头文件、`lidar_target_tracking` 点云桥接与状态发布、正式 bringup 接线，以及 Web 观测和选点接口。原始包的 `package.xml` 声明 MIT；复制头文件没有被项目适配代码改写。用户在 Jetson 现场验收后报告跟踪效果“还可以”；未记录速度、路线或持续时间，因此该评价只覆盖当次试验。

Web 的选点操作在 manual 模式打开的跟踪视图中进行；HTTP `202` 只确认选点消息发布。跟踪节点不设置原版速度回调，也不创建速度发布者。跟踪状态的目标值在未匹配时保留最后输出，不能解释为本帧确认目标。

三个复制头文件与固定参考提交的对应文件逐一 `cmp` 相同。原版移植时，`lidar_target_tracking` 的三个 CTest 目标、`robot_web_ui` 的十个 CTest 目标、Web 资产 43 项及 `system_bringup` Python 测试 759 项通过；`colcon test-result --all --verbose` 汇总 863 项、零失败。Web CTest 需要允许本地 socket 和可写 ROS 日志目录。选定包的 `colcon build` 在 `robot_web_ui` 的 CMake 构建返回成功后，于安装步骤未结束；`colcon test` 在执行首个 CTest 前未结束，完整工作区构建则在 `can_driver` 超过 90 秒未结束，因此这些命令没有完整结果。DDS 端到端传输、Gazebo 行为仍缺证据；现场评价只有用户反馈，没有量化记录。

## Alternatives considered

**沿用高度带、聚类或预测关联。** 这些会改变参考实现收到的点和选目标规则，无法隔离原版效果；本次只取一条原始水平环并保留原版搜索圆与质心计算。

**默认启用滤波或新增丢失超时。** 两者都改变原版输出。参考实现默认关闭滤波，搜索圆没有匹配回波时不按时长宣告丢失；本次保持这些默认值。若现场效果不足，后续单独设计改进。

**专用静止验证启动链。** 现有 `mapping` 或 `navigation` 完整启动且不发目标即可验证；另起一套启动入口会增加代码和运行差异。

**复制参考 Web 或直接发布跟随速度。** Web 展示不是跟踪核心算法，现有抽屉交互更适合本仓库；车辆运动属于后续 Nav2 集成，本次只输出观测。

## Verification

自动化检查覆盖环号选择、坐标方向、角格空值与同格最近点，以及原版搜索与默认滤波行为。Web 回归覆盖三种页面模式、gate 接管与恢复、抽屉显示、跟踪画布平移和视图按钮、双击坐标、手动行驶输入屏蔽及原有地图行为。跟踪节点不存在速度发布者，不发送 Nav2 目标。用户已完成一次 Jetson 现场验收并报告效果“还可以”，但没有提供可复现的运动工况记录。

## Consequences

单环可能漏掉人体、被车体遮挡，或混入背景；原版搜索圆也可能在快速移动时漏匹配。原版保留最后位置不等于当前位置可信，页面将该位置标为最后一次参考输出，不承诺目标身份或失联自动找回。保留原版卡尔曼实现不代表其数学正确性已验证，默认关闭避免把滤波效果混入首次比较。跟踪页保持 gate 为 `manual`，车辆跟随接入 Nav2 时需要重新设计速度源切换。

完整系统仍包含原有控制与导航组件，静止验证必须保持不发导航目标且不操作手动行驶。已有 Nav2 goal 在手动接管后不会自动取消；gate 只阻断其速度。静态构建与自动化测试不能证明运动小车的跟随效果。
